## 3. 核对 c：阶段标注（Stage 1~6）与 plan §31；MVP=Stage 0-1 切分

PRD §13 已声明"阶段标注由蓝图 §31 交付物映射推导，未经逐条用户确认"——标注本身是合法的新增层。逐 Stage 核对结果：

### 3.1 实质冲突 1 处：FR-068（企业审计导出，Must·Stage 3）

- plan §31 Stage 3 交付：Postgres/S3、API/worker、项目与角色、SSO 基础、策略/审批、资产版本灰度、Domain Studio、OTel/队列/备份、垂直包影子——**无审计导出**。
- plan §31 Stage 4 交付：**"数据驻留、BYOK、保留/删除、审计导出"**——审计导出明确在 Stage 4。
- PRD §4.7 将 FR-068 标 Stage 3；PRD §6.2 又写"多租户/ABAC/驻留/BYOK/审计导出 → Stage 4（FR-070～074）"并附 NOTE"审计导出（FR-068）……考虑把 JSON 只读导出前移"——**PRD 内部 §4.7 与 §6.2 打架，且整体与底稿 §31 不一致**。
- 建议：统一为一种表述。若坚持 Stage 3，应标注 [ASSUMPTION] 并说明与底稿 Stage 4 的偏离是有意前移；否则改回 Stage 4。

### 3.2 轻微超出 1 处：FR-044 的"影子测试"入 Stage 1·★MVP

- plan §31 Stage 1 交付仅"规则 DSL/Python 局部模型、历史回放和沙箱"；"影子"字样首次出现在 Stage 4（世界模型影子）；AC-05 只要求历史回放。
- plan §13.6 允许"影子期**或人工批准**"二选一激活，故 Stage 1 全量实现影子测试并非底稿要求。
- 建议：FR-044 Stage 1 范围改为"静态、回放、性质测试（影子或人工批准）"，或把影子测试明确为 Stage 1 的可选路径，与 FR-045（Stage 4）的 shadow 状态解耦。

### 3.3 MVP=Stage 0-1 切分 vs §31/§39

- **与 §31 不冲突**：MVP="单机闭环"正是 Stage 1 目标；PRD 注明 Stage 0 是前置活动不产交付需求，与 §31 Stage 0 性质（访谈/基线/意向，无功能交付）吻合；MVP 验收挂 AC-01~08 与 §32.1"技术 MVP 验收"对应正确。
- **与 §39 有一处未对齐**：90 天计划第 61-90 天含"完成 Tool Proxy 或 Playwright 适配器"与"至少一个外部团队 L0 接入"（时间上落在 Stage 0-1 窗口内），PRD 将二者划入 Stage 2（§6.2，与 §31 一致）。PRD 声称 MVP 切分"依据 Stage 1 交付物**与 90 天计划**推导"，实际以 §31 为准、§39 后段未纳入 MVP 也未明示这一取舍（Tool Proxy 去向有交代，外部接入属活动非需求）。属可辩护的推断，建议在 [ASSUMPTION] 中补一句"90 天计划末段的外部接入预演按 §31 归 Stage 2"。
- **内部计数错误**：§6.1 与 §13 两处声称"标 ★MVP 的 **24** 条 FR"，但正文实际标注 ★MVP 的为 **34 条**（grep 计数 34；§6.1 括号内列举的编号本身完整且与 34 条一致：FR-001/004/005、010~014、020~025、030~033、035~037、040/041/043/044/046~048、052/053、060/062~064 = 3+5+6+4+3+7+2+4 = 34）。**数字 24 是笔误，会误导 MVP 排期与工作量评估，须改。**

### 3.4 其余 Stage 标注抽查结论

Stage 1（34 条 ★MVP）全部能在 §31 Stage 1 交付或 §39 90 天计划中找到出处（FR-013/014 图像 inspect/Diff 出自 §39 第 31-60 天；FR-047/048 规划约束出自 §13.8 体系内）。Stage 2~6 标注与 §31 交付物的对应见 §1.1 表"备注"列；除 §3.1/§3.2 两处外无矛盾。FR-029/055/069/079/085 等为无底稿明确对应的弱推断，PRD §13 已统一披露，可接受。
